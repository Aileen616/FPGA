# 返回后左移对齐卡住的原因

本轮只读分析现有日志与部署快照；无源码/参数修改、无硬件访问、无发车。

## 路径与返回判定

实测图及节点事件显示软件序列0→1→2→3→4（右侧死路）→3。节点4的父节点3、唯一出口左；节点3返回后completed=2（右支路完成）、tried=10（右和左已尝试）。选择左侧未探索支路符合完整探索策略，并不是立即退到起点的模式。

软件已接受返回节点3，不是卡在“等待识别父节点”。但返回检查仅核对既定父节点、出口组合和来路侧局部距离，不能据此宣称实物已精确回到原节点中心。地图记录的return_error_mm=172，是编码器里程x/y误差绝对值之和，可能包含打滑、计程误差与停车位置变化；不是外部实测车身偏移172mm。目前它只记录/上报，不用于纠正ToF控制。

## 可确定的直接卡点

返回后向左探索，前方探头形成新开口事件（PM1）。events按运动轴上的墙距作为锚点，套用target=edge_distance-corridor_width/2；本次EDGE352、通道600，得到左侧净距目标52mm。52指最终应保持的净距，不是待移动52mm。

move的原执行预算为当前主向净距减margin35、brake10、error50，共95mm。净距到95mm附近后允许的左移推进趋近0；但ALIGN仍要求净距达到52mm附近（容差5mm）才结束。约87～95mm的读数下，状态仍ALIGN、RY0，地图位置保持，形成不可达目标导致的停滞。ALIGN没有按entered_ms计时退出，这解释了它为何保持WHY0等待，而非自行报错；最终STATE13/WHY10来自用户授权停车。

日志在左向CROSS阶段还曾记录EDGE1145/TARGET845，之后新开口重新登记EDGE352/TARGET52，说明后续开口定位覆盖了上一段对齐目标；不是地图把52mm作为回程路长发送给车辆，也不是编码器直接生成该控制目标。

## 根因边界与后续修改重点

确定的软件缺口是开口对齐目标生成没有与原执行预算保持一致，能够生成根本到不了的目标。当前资料未冻结EDGE352形成瞬间的原始帧与滤波缓存，因此不能唯一解释为何边界只剩352mm；开口观测时刻、局部墙面几何以及返回定位偏差都需要结合原始事务核对，不能直接断言是某个探头坏了或返回节点匹配错了。

后续应优先修正开口/参考墙的几何定位和目标可达性衔接，并核对回到已知节点时的实际局部距离。不能仅把52硬改为95或降低原余量，因为这样未必停在正确路口中心。本次只分析，未实施修改。
